# 04 链路选型：延迟、配额与反模式

## 延迟预算

| 链路 | 单程延迟量级 | 抖动 | 断网表现 | 适合的控制周期 |
|---|---|---|---|---|
| 板载直连 IO | 1–10 ms | 小 | 无影响 | 10–20 ms |
| 局域网 MQTT | 20–80 ms | 中 | 依赖 AP | 100–200 ms |
| 公网 MQTT（厂商云） | 300 ms–2 s | 大 | 完全失联 | ≥ 1 s（宏动作） |
| HTTP 轮询 | 比 MQTT 更差 | 大 | 完全失联 | 不建议做控制 |

上表是量级判断，不是实测值。请把自己环境的数字补进 `docs/06` 的验证记录。

## 配额与硬限制（以常见教育机器人 IoT 平台为例）

| 项 | 典型值 | 影响 |
|---|---|---|
| 设备（topic）数量 | 10 个/账号 | 多机协作要提前规划 topic 分配 |
| 单设备消息缓存 | 1000 条滚动覆盖 | 上行频率不能太高；遥测要降采样 |
| 账号总记录 | 10000 条 | 长时间运行会被覆盖，重要状态要落本地 |
| WiFi 频段 | 仅 2.4 GHz | 5 GHz-only 环境直接连不上，需开热点 |
| 指令透传形态 | 字符串比对 | 参数只能分档，不能连续 |

这些限制不是"平台做得差"，而是"平台没打算做实时控制"。把它当消息通道，而不是当控制器。

## 决策树

```
需要公网远程？
├─ 是 ──▶ 需要实时控制？
│         ├─ 是 ──▶ 两级结构：板载反射环 + 云端任务层
│         └─ 否 ──▶ 云端 topic，宏动作即可
└─ 否 ──▶ 控制器能跑 Linux/Node？
          ├─ 是 ──▶ 板载 Agent（最优）
          └─ 否 ──▶ 局域网 broker + 宏动作
```

## 两级结构的最小实现

```
云端 Agent          板载程序
  │  set_mode(follow)  │
  │ ─────────────────▶ │  进入 50ms 反射环
  │                    │  视觉→差速→电机（本地闭环）
  │  ◀───────────────  │  事件：LOST / BLOCKED / DONE
  │  follow_off()      │
  │ ─────────────────▶ │  停车，退出反射环
```

要点：**云端只发"模式与参数"，不发"每帧动作"**。事件上行要节流（同一事件 2 秒内只报一次），否则会把 1000 条缓存刷满。

## 反模式清单

| 反模式 | 症状 | 修法 |
|---|---|---|
| 云端逐帧发速度 | 动作一顿一顿，越跟越偏 | 控制环下沉到板载/控制器 |
| 高频遥测（每 50 ms 一条） | 缓存滚掉关键状态 | 降采样 + 变化上报 |
| 无 ACK 连发指令 | 指令被覆盖，动作随机 | 序号 + ACK + 等确认 |
| 断网无看门狗 | 机器人一直往前冲 | 板载 3 秒超时自动停 |
| 一条消息塞多个字段却不带分隔 | 解析歧义 | 固定格式 + 版本号 |
| 把 topic 当数据库 | 记录被滚动覆盖 | 关键数据落本地文件 |

## 什么时候值得加一道"本地 broker"

只有一个理由：**把 300 ms–2 s 降到 30–80 ms**，让宏动作变得跟手。做法通常是把通信模块里可配置的服务器地址指向局域网内的 broker。

先做三件事再改：

1. 用 MQTT 客户端工具，以原厂账号密码连本地 broker，发一条"停车"，确认机器人响应；
2. 确认模块是否强制 TLS / 特定 ClientID / 特定 topic 前缀；
3. 保留回滚路径（原厂地址截图保存）。

三条都过再改程序，否则你会同时怀疑三个变量。
