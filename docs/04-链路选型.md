# 04 链路：多快、能传多少、哪些做法是坑

## 各条链路有多快

| 链路 | 单程延迟 | 稳不稳 | 断网会怎样 | 适合多快的控制 |
|---|---|---|---|---|
| 直接接在板子上 | 1–10 毫秒 | 稳 | 不受影响 | 10–20 毫秒 |
| 同一个局域网内转发 | 20–80 毫秒 | 一般 | 看路由器 | 100–200 毫秒 |
| 厂家云平台转发 | 300 毫秒–2 秒 | 抖得厉害 | 完全失联 | 只能做整套动作 |
| 网页轮询 | 比上面更差 | 抖 | 完全失联 | 不建议用来控制 |

表里是量级，不是实测值。把自己环境里的数字补进 `docs/06` 的记录表。

## 平台本身的限制（以常见教育机器人 IoT 平台为例）

| 项 | 典型值 | 对你的影响 |
|---|---|---|
| 能挂多少个设备（topic） | 每个账号 10 个 | 多台机器要提前分好 |
| 单个设备消息缓存 | 1000 条，满了覆盖旧的 | 上报别太频繁 |
| 账号总记录 | 10000 条 | 跑久了会被覆盖，重要状态存本地 |
| WiFi 频段 | 只有 2.4GHz | 只有 5G 的环境连不上，得开热点 |
| 指令形式 | 字符串比对 | 参数只能分档，不能连续 |

这些不是平台做得差，是**平台本来就没打算做实时控制**。把它当发消息的地方，别当控制器。

## 怎么选（照着走）

```
要不要公网远程？
├─ 要 ──▶ 要不要实时控制？
│         ├─ 要 ──▶ 两级：机器人上做快反应，云端做任务
│         └─ 不要 ──▶ 云端发字符串，做整套动作就行
└─ 不要 ──▶ 主控能不能跑 Linux/Node？
          ├─ 能 ──▶ 把 AI 放到机器人上（最好）
          └─ 不能 ──▶ 局域网转发 + 整套动作
```

## 两级结构最少要写成什么样

```
云端 AI                机器人上的程序
  │  切到跟随模式        │
  │ ─────────────────▶ │  进入 50ms 的反应环
  │                    │  看到人 → 算左右 → 电机（本地闭环）
  │  ◀───────────────  │  事件：丢了目标 / 被挡住 / 做完了
  │  退出跟随            │
  │ ─────────────────▶ │  停车，退出反应环
```

要点：**云端只发"模式"和"目标"，不发"每一帧怎么动"**。事件要节流：同一件事 2 秒内只报一次，否则会把 1000 条缓存刷满。

## 常见错误做法

| 做法 | 会出现什么 | 怎么改 |
|---|---|---|
| 云端一帧一帧发速度 | 动作一顿一顿，越跟越偏 | 把控制环放到机器人身上 |
| 每 50 毫秒上报一次 | 缓存滚动，关键状态没了 | 降频 + 变了才报 |
| 连发指令不等确认 | 指令互相覆盖，动作随机 | 加序号 + 回确认，等确认再发 |
| 断网没有自动停车 | 机器人一直往前冲 | 车上做 3 秒超时自动停 |
| 一条消息塞好几个值，又不加分隔 | 解析乱了 | 固定格式 + 版本号 |
| 把平台当数据库用 | 记录被覆盖 | 关键数据存本地 |

## 什么时候值得加一台"局域网转发"

只有一个理由：**把 300 毫秒–2 秒降到 30–80 毫秒**，让整套动作跟手一点。

做法通常是把通信模块里能填的服务器地址，改成局域网内那台机器。

改之前先做三件事：

1. 用 MQTT 客户端，拿原来的账号密码连本地，发一条"停车"，看机器人有没有反应；
2. 确认模块有没有强制加密、指定 ClientID、指定 topic 前缀；
3. 留好退路（把原来的地址截图存下来）。

三条都过再改程序，否则你会同时怀疑三个变量。
