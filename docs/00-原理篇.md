# 00 原理：为什么"反应快慢"决定了一切

后面所有表格和清单，都是从这三条推出来的。型号只改参数，原理不变。

## 一、反应有多快，决定能做多细的动作

控制就是"看一眼、动一下、再看一眼"。

你隔 1 秒才看一眼，这 1 秒里车已经跑出去半米，你再动，就是在追一个已经不在原地的目标。

换算到中鸣的车：底盘从静止到跑起来，大约 0.2–0.5 秒。想让车跟住人，程序必须 **50–100 毫秒**看一次。

而 IoT 模块走一圈网络要 **0.5–2 秒**。这个速度下，只能做"整套动作"（前进一段、转个弯、停），做不了"往左一点、再往左一点"。

**结论**：把 AI 放到更远、更慢的地方，不是让它更聪慧，是让它更迟钝。

## 二、先算"要多快"，再决定"谁来做"

顺序不能反：

```
要做的事 → 必须多快看一次 → 允许的最大延迟 → 谁来做
```

| 要做的事 | 必须多快看一次 | 谁来做 |
|---|---|---|
| 跟着人走、对准了再抓 | 20–50 毫秒 | 只能在机器人身上 |
| 定距跟随、躲障碍 | 100–200 毫秒 | 机器人身上，或同一个局域网 |
| 巡线、走固定距离 | 50–100 毫秒 | 机器人身上（主控里写程序） |
| "走到桌前，再抓红块" | 秒级 | 云端可以 |
| "有人挡就绕，绕不开叫我" | 秒级 | 云端可以 |

分成两层，本质是把"慢的决定"和"快的反应"分开，互不拖累：网卡了不影响车稳，板上算力不够也不影响它听懂任务。

传数据也要省着用：上行慢，就只传"状态变了"，别传原始数据流。

## 三、给多少信息，就只能做多聪明的判断

感知就是"把世界简化"：简化成一个数字、一个方向、一组坐标、一帧画面。简化得越狠，后面能做的判断越少。

- **只要 1 个答案**（近/远、碰到/没碰到、黑线/白底）→ 只能做"近了就停"。
- **要一个方向和大小**（偏左多少）→ 能做"往左修一点"。
- **要画面或一组坐标** → 才能判断"这是人还是椅子、能不能过去、该抓哪个"。

所以"有 AI 视觉模块"不等于"能做视觉判断"：模块把画面压成了"类别 + 位置"，AI 拿到的信息只够做方向修正。想往上走，先看感知通道是不是被压成了一个数，别急着换更大的模型。

**结论**：模型再强，也强不过它看到的那点信息。

## 正确的思考顺序

1. 写清要做的事，多久要决策一次？
2. 由此算出最多能容忍多少延迟。
3. 按这个延迟选链路、定谁在哪（见 `04-链路选型.md`）。
4. 再看传感器给的信息够不够支撑这种判断（见 `03-传感器矩阵.md`）。
5. 最后才回答"要不要 Agent"（见 `01-三层模型.md`）。

顺序反了，就会先买板子、先接平台，回头发现太慢、看不清，再返工。

## 三个容易想错的地方

| 想错的地方 | 实际情况 |
|---|---|
| 模型越强，机器人越智能 | 信息不够时，强模型只是在猜 |
| 能连上就等于能控制 | 连得上不等于够快，1 秒的链路只能做整套动作 |
| 分几层是"架构设计" | 分几层是被延迟和信息量逼出来的，不是审美 |
