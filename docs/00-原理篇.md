# 00 原理篇：三个问题的底层依据

前面所有矩阵和清单，都是从三条原理推出来的。原理不随型号变，型号只改参数。

## 原理一：可控性由延迟决定

控制环的本质是"看一眼、动一下、再看一眼"。每 T 秒才看一次，对象在这 T 秒里已经变了；T 越大，控制器依据的信息越旧，动作就越像在追一个已经不在原地的目标。

工程上的经验值：**控制频率取被控对象带宽的 5–10 倍**；理论下限是 2 倍（采样定理），低于它一定会漏掉对象的快速变化。

换算到机器人：轮式底盘的时间常数大约 0.2–0.5 s，对应控制周期 50–100 ms。链路延迟一旦超过 1 s，无论模型多聪明，都只能做"宏动作"——因为在这 1 秒里，底盘已经走出半米。

**推论**：把决策放到延迟更大的地方，等于主动降低可控带宽。这不是"更聪明"，是"更慢"。

## 原理二：分层由延迟预算反推

正确的顺序不是"先决定用几层，再想办法实现"，而是反过来：

```
任务 → 需要多快的闭环 → 允许的最大延迟 → 决策层只能放在哪
```

| 任务 | 需要的闭环周期 | 可行的决策位置 |
|---|---|---|
| 视觉伺服、抓取对准 | 20–50 ms | 只能在机上 |
| 定距跟随、避障 | 100–200 ms | 机上，或局域网链路 |
| 巡线、定距行走 | 50–100 ms | 机上 |
| "走到桌前再抓红块" | 秒级 | 云端可以 |
| "途中有人挡就绕，绕不开叫我" | 秒级 + 事件 | 云端可以 |

两级结构的本质，是把"慢决策"和"快反射"拆到两个时间尺度上，让它们互不拖累：云端抖动不影响控制稳定性，板上算力不够也不影响任务理解。

事件上行要节流，原理同样简单：上行带宽有限时，只传**状态变化**，不传原始流。变化检测就是边缘触发，等价于在源头做了一次压缩。

## 原理三：智能层级由信息带宽决定

感知的本质是降维：真实世界 → 一个数值 / 一个类别 / 一组坐标 / 一帧图像。降得越狠，后面能做的判断越少。

- **判定**只需要 1 bit：近 / 远、碰到 / 没碰到、黑线 / 白底。
- **定向**需要一个带符号的量：偏左多少、偏右多少。
- **场景理解**需要空间结构：这是什么、能不能过去、该抓哪一个。

所以"有 AI 视觉模块"不等于"能做视觉智能"——模块把画面压成了"类别 + 坐标"，Agent 拿到的信息量本来就只够定向动作。想往上走，先别急着换更大的模型，先看感知通道是不是被压成了单值。

**推论**：模型能力和感知带宽必须匹配。带宽不足时，更强的模型只是在更自信地猜。

## 三条原理的用法：反推法

1. 写清任务的时间尺度：多快需要决策一次？
2. 由它算出允许的最大延迟。
3. 用延迟预算选链路、定层次（见 `04-链路选型.md`）。
4. 再看感知通道的分辨率够不够支撑这类判断（见 `03-传感器矩阵.md`）。
5. 最后才回答"要不要 Agent"（见 `01-三层模型.md`）。

顺序反了，就会先买板子、先接平台，再发现延迟不够、感知不够，然后回头重做。

## 三个常见谬误

| 谬误 | 实际情况 |
|---|---|
| 模型越强，机器人越智能 | 带宽不够时，强模型只是在猜；决策精度受限于感知分辨率 |
| 能连上就等于能控制 | 通道存在 ≠ 延迟达标；1 s 的链路只支持宏动作 |
| 分层是架构审美 | 分层是被延迟和带宽逼出来的，不是设计偏好 |
