> **一句话**：能不能让 AI Agent 操控一台机器人，不取决于 Agent 有多强，而取决于三件事——**Agent 在哪、指令怎么进去、感知怎么回来**。

给定一台机器人，先看控制器能开放到哪一层，再看传感器能给出多少信息，最后才决定链路与 Agent 的分工。换一台机器、换一批传感器，框架不变，只换参数。

本仓库以**思路与原理**为主：矩阵是结论，`docs/00` 讲结论的来处，`examples/` 里的代码只作参考实现，不是主体。

> **第一次来？** 先看 [大白话版](docs/07-大白话版.md)。

> **说人话版**：中鸣主控（E6/E7/M5/M6/E3/C7）只能跑下载进去的程序，外面没法实时改它。
> 要么加 IoT 模块、发字符串让它执行你写好的动作；要么把主控换成能装系统的板子（H-RCU、灵芯派）；
> 要么干脆把跟随、巡线这类功能直接写进主控。三条路各自的代价，大白话版里写清楚了。

## 三个问题

| 问题 | 它决定什么 | 常见错误 |
|---|---|---|
| **Agent 在哪？** | 闭环频率的上限 | 让云端 Agent 做逐帧控制，延迟一秒，目标早跑了 |
| **指令怎么进去？** | 可下发的参数粒度 | 以为"能连上"就等于"能控制" |
| **感知怎么回来？** | Agent 能做什么级别的判断 | 拿一个数字当图像用，指望它做视觉伺服 |

## 一张图

```text
              ┌──────────────────────────────────┐
              │        AI Agent（决策层）          │
              │    板载或云端 · 发任务 · 收事件     │
              └───────────────┬──────────────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
     云端 topic          局域网 broker        板载 Agent
     0.5–2 s             30–100 ms           10–50 ms
     公网可达             仅同网段             无网络依赖
     字符串/分档           字符串/分档          数值/连续
          │                   │                   │
          └───────────────────┼───────────────────┘
                              ▼
              ┌──────────────────────────────────┐
              │        控制器（执行层）            │
              │     固件程序 → 电机 / 舵机         │
              └───────────────┬──────────────────┘
                              ▼
              ┌──────────────────────────────────┐
              │        传感器（感知层）            │
              │   视觉 · 超声 · 编码器 · IMU       │
              └──────────────────────────────────┘
```

**关键约束**：`闭环周期 ≥ 感知更新周期 + 链路延迟 + 执行响应`。
等式不成立，控制就会抖、会丢、会过冲。这一条决定了后面所有的选型。

## 三条链路

| 链路 | 延迟量级 | 可达性 | 参数粒度 | 成本 | 适用 |
|---|---|---|---|---|---|
| **云端 topic**（厂商 IoT 平台类） | 0.5–2 s | 公网可达 | 字符串 / 分档 | 一个通信模块 | 演示、远程、跨地点 |
| **局域网 broker** | 30–100 ms | 仅同网段 | 字符串 / 分档 | 一台常开主机 | 教室、家里、展会 |
| **板载 Agent** | 10–50 ms | 无网络依赖 | 数值 / 连续 | 一块算力板 | 闭环控制、视觉伺服 |

三种不是替代关系，是**算力放在哪**的问题。板载负责反射，云端负责任务编排，是可以叠加的两级结构。

## 30 秒决策

| # | 你的情况 | 结论 |
|:--:|---|---|
| 1 | 控制器是单片机、只能下载固件 | 走 topic 链路，动作做成**宏动作**，别做逐帧控制 |
| 2 | 控制器能跑 Linux / Node | **板载 Agent**，工具层直接接 IO，闭环可做 |
| 3 | 既要公网可达又要低延迟 | **两级**：板载做反射环，云端只发任务、收事件 |
| 4 | 需求只是单一功能（例如跟随） | 很可能**不需要 Agent**，确定性控制更稳 |

## 怎么用

1. **完全不想看术语** → 先读 [`docs/07-大白话版.md`](docs/07-大白话版.md)
2. **手上有一台具体机器** → 用 [`docs/02`](docs/02-控制器矩阵.md) 和 [`docs/03`](docs/03-传感器矩阵.md) 填自己手上的型号
3. **要选链路** → 按 [`docs/04`](docs/04-链路选型.md) 的延迟预算反推
4. **要跑 demo** → 照 [`docs/06`](docs/06-复现清单.md) 一步步验证

> 矩阵里标"待实测"的格子，就是最值得先动手验证的地方。

## 贡献与团队

欢迎补型号、补实测数据。提交时请注明：**控制器型号 + 固件版本 + 链路 + 实测延迟 + 结论**。见 [`CONTRIBUTING.md`](CONTRIBUTING.md)。

本手册由 **无隐创新（IN：Innovation, Nothing Hidden）** 团队发起并维护。写它的原因很实际：我们自己在给不同控制器接 Agent 时，每次都卡在同样三个问题上，于是把结论沉淀成矩阵，换型号只需重填格子，不必从头再试一遍。

团队缩写 **IN** 取自两个词：**I** = Innovation，**N** = Nothing（hidden）。中文读作"创新，无所隐藏"，也就是"无隐创新"；英文把 Innovation 放前面，缩写才好读成 IN。

这份矩阵是我们对外公开的部分结论。矩阵里空着的格子，欢迎你带着实测数据来填。
