# 把 Agent 接进机器人

> 控制器 · 传感器 · 链路：接入前要判断的三件事

一句话：**能不能让 AI Agent 操控一台机器人，不取决于 Agent 有多强，而取决于三件事——Agent 在哪、指令怎么进去、感知怎么回来。**

这份文档不绑定厂商，也不绑定型号。它记录的是一套判断框架：给定一台机器人，先看控制器能开放到哪一层，再看传感器能给出多少信息，最后才决定链路和 Agent 的分工。换一台机器、换一批传感器，框架不变，只换参数。

本仓库以**思路与原理**为主：矩阵是结论，`docs/00` 讲结论的来处，`examples/` 里的代码只作参考实现，不是主体。

本手册由 **无隐创新（IN：Innovation, Nothing Hidden）** 团队发起并维护。写它的原因很实际：我们自己在给不同控制器接 Agent 时，每次都卡在同样三个问题上，于是把结论沉淀成矩阵，换型号只需重填格子，不必从头再试一遍。

## 三个问题

| 问题 | 它决定什么 | 常见错误 |
|---|---|---|
| Agent 在哪？ | 闭环频率的上限 | 让云端 Agent 做逐帧控制，延迟一秒，目标早跑了 |
| 指令怎么进去？ | 可下发的参数粒度 | 以为"能连上"就等于"能控制" |
| 感知怎么回来？ | Agent 能做什么级别的判断 | 拿一个数字当图像用，指望它做视觉伺服 |

## 三层模型

| 层 | 职责 | 典型承担者 |
|---|---|---|
| 感知 | 把世界变成结构化信号 | 视觉模块、超声、编码器、IMU |
| 执行 | 把信号变成电机/舵机动作 | 控制器 + 固件程序 |
| 决策 | 决定"做什么、先做什么、出错怎么办" | Agent（板载或云端） |

关键约束：**闭环周期 ≥ 感知更新周期 + 链路延迟 + 执行响应**。等式不成立，控制就会抖、会丢、会过冲。这一条决定了后面所有的选型。

## 三条链路

| 链路 | 延迟量级 | 可达性 | 参数粒度 | 成本 | 适用 |
|---|---|---|---|---|---|
| 云端 topic（厂商 IoT 平台类） | 0.5–2 s | 公网可达 | 字符串/分档 | 一个通信模块 | 演示、远程、跨地点 |
| 局域网 broker | 30–100 ms | 仅同网段 | 字符串/分档 | 一台常开主机 | 教室、家里、展会 |
| 板载 Agent | 10–50 ms | 无网络依赖 | 数值/连续 | 一块算力板 | 闭环控制、视觉伺服 |

三种不是替代关系，是**算力放在哪**的问题。板载负责反射，云端负责任务编排，是可以叠加的两级结构。

## 30 秒决策

1. 控制器是单片机、只能下载固件？→ 走 topic 链路，动作做成"宏动作"，别做逐帧控制。
2. 控制器能跑 Linux / Node？→ 板载 Agent，工具层直接接 IO，闭环可做。
3. 既要公网可达又要低延迟？→ 两级：板载 Agent 做反射环，云端 Agent 只发任务和收事件。
4. 需求只是单一功能（例如跟随）？→ 很可能**不需要 Agent**，确定性控制更稳（见 `docs/01`）。

## 怎么用

先读 `docs/00` 弄清三条原理，再读 `docs/02` 和 `docs/03` 填自己手上的型号，然后读 `docs/04` 选链路，最后按 `docs/06` 一步步验证。矩阵里标"待实测"的格子，就是最值得先动手验证的地方。

## 关于无隐创新

无隐创新是一个做机器人与 AI 接入的小团队。我们不生产控制器，也不替代厂商的软件，只研究一件事：**怎么让 Agent 在不破坏原有硬件的前提下，真正把机器人用起来。**

团队缩写 **IN** 取自两个词：**I** = Innovation，**N** = Nothing（hidden）。中文读作"创新，无所隐藏"，也就是"无隐创新"；英文把 Innovation 放前面，缩写才好读成 IN。

这份矩阵是我们对外公开的部分结论。矩阵里空着的格子，欢迎你带着实测数据来填。
